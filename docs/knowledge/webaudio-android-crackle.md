# Web Audio が Android の Chrome でだけぶつぶつする

テンプレートから作るどのゲームでも起こりうる、Web Audio の音切れ（ぶつぶつ・数秒の無音）と、その調べ方。処理が間に合わないこと以外でぶつっと鳴る原因も、後半にまとめる。調べる順番と道具は skill `mobile-audio-render`（[agent-skills](https://github.com/takumifukasawa/agent-skills) の `gamedev/`。`scripts/` に記録の道具とテストページがある）。描画の重さとの切り分けもここに書く（描画を軽くする設定は [three-render-cost.md](three-render-cost.md)）。

## 鳴り終わった音の部品をつないだままにすると、時間とともに重くなる

- 症状: PC と iPhone では平気なのに、Android の Chrome（例: Pixel 5）でだけぶつぶつする。プレイが進むほどひどくなり、ひどいと数秒無音になって戻る。音量・残響・描画・出力バッファを変えても、減るだけで消えない。
- 原因: 1 音ごとに `OscillatorNode` / `AudioBufferSourceNode` と、その後ろの `GainNode` / `BiquadFilterNode`（音量の包絡、フィルター、残響への送り）を作って、共通の出口（マスター・残響のバス）につなぐ。この作り方で、音源が止まった後も、後ろの部品を出口につないだままにしていた。Chrome は、JS の GC がそれらを回収するまで、無音の部品も毎回の音の処理でたどる。毎秒数十個ずつ増え続けるので、音の処理時間がだんだん伸びる。そしてやがて、1 回分（128 サンプル、48kHz で 2.7ms）の締め切りに間に合わなくなる。メモリに余裕があるほど GC が遅く、溜まる量が多い。速い端末では締め切りに間に合ってしまうので、表に出ない。
- 対策: 音源の `ended` で、その音のために作った部品を全部 `disconnect()` する。

  ```ts
  function releaseWhenDone(source: AudioScheduledSourceNode, ...nodes: AudioNode[]): void {
      source.addEventListener("ended", () => {
          source.disconnect();
          for (const n of nodes) n.disconnect();
      }, {once: true});
  }
  // 1 音: osc -> filter -> env -> (dry -> master, send -> reverb)
  osc.start(t);
  osc.stop(t + decay + 0.05);
  releaseWhenDone(osc, filter, env, dry, send);
  ```

  音源が 2 つある音（倍音を足すなど）は、同じ時刻に止まる片方の `ended` で、もう片方と共通の部品をまとめて外す。和音の切り替えでフェードアウトさせた古い声も、同じように外す。
- 実測（ある 1 本のゲーム、Pixel 5、約 50 秒のステージ）: 間に合わなかった回数は、開始時が毎秒 5 回、終盤が毎秒 290 回、ステージ全体で 8097 回だった。外すようにすると 511 回になった。1 回の処理の中央値は 2.5ms → 1.1ms。
- 再発したら: 同時に鳴っている音の数は一定なのに、処理時間がプレイ時間に比例して伸びていたら、まずこれを疑う。

## 出力バッファ（`latencyHint`）で余裕を持たせる

- Android の Chrome は、`new AudioContext()`（既定は `"interactive"`）だと 128 サンプルずつ（`baseLatency` 約 3ms）鳴らす。たまに重くなる瞬間（音を一度に多く鳴らす演出など）があると、それだけで途切れる。
- `new AudioContext({latencyHint: "balanced"})` にすると、Pixel 5 では `baseLatency` が 20ms、`outputLatency` が 24ms → 56ms になった。上の対策と合わせると、間に合わなかった回数は 511 → 41 回に減った。指定は効く（効いたかは `ctx.baseLatency` で確かめる）。
- `"playback"` はもっと大きくなるはずだが、Pixel 5 ではかえって途切れが増えた（同じ条件で `balanced` 0 回、`playback` 24 回）。大きいほど良いとは限らないので、実機で回数を比べて選ぶ。
- 代わりに音が約 30ms 遅れる。拍に合わせて先に予約して鳴らす音や、通過の瞬間に鳴らす音なら、遅れには気づきにくかった。タップへの即時の反応音が大事なゲームでは、耳で確かめてから決める。

## 毎フレーム同じ値をオートメーションに送らない

- 毎フレーム `param.setTargetAtTime(target, now, tc)` を呼ぶと、目標が変わっていなくても予定（イベント）が積まれる（例: 5 か所 × 60fps で毎秒約 300 回）。音切れの決め手ではなかったが、無駄なので、目標か時定数が変わったときだけ送る（変化が 2% 以内なら送らない、など）。

## 調べ方: PC で再現しなければ、実機を USB でつないで記録する

推測で設定を変えた URL を実機で試してもらうのは、何往復もかかるうえに、当たらないことが多かった。実機の Chrome の中で音の処理の時間を直接記録すれば、1 回で分かる。

1. 実機で「開発者向けオプション → USB デバッグ」をオンにして、データを送れるケーブルでつなぐ。Mac に何も出ないときは、ケーブルが充電専用のことが多い（Mac の USB 機器の一覧で確かめる: `ioreg -p IOUSB`）。adb を入れる: `brew install android-platform-tools`。
2. `adb devices` に出たら、`adb forward tcp:9222 localabstract:chrome_devtools_remote`。`ws://localhost:9222/devtools/browser` に CDP でつなぐ。
3. `Target.createTarget` でゲームを開き、`Target.attachToTarget`（flatten）→ `Target.activateTarget`。音を鳴らし始めるには、ユーザー操作が要る。`Input.dispatchTouchEvent` でページにタップを送る（`adb shell input tap` は、端末で前面に出ている別のアプリを押してしまうことがある）。
4. `Tracing.start`（`includedCategories: ["webaudio", "audio", "toplevel"]`、`transferMode: "ReturnAsStream"`）。遊ばせて、`Tracing.end` → `IO.read` で保存する。
5. 見るもの:
   - `Glitch!` と `SyncReader::Read timed out`（締め切りに間に合わなかった）を、1 秒ごとに数える。時間とともに増えていたら、上の「つないだまま」を疑う。
   - `RealtimeAudioDestinationHandler::Render` の時間（1 回分の音を作る時間）。128 サンプルなら 2.7ms を超えると途切れる。
   - `args.frames` / `playout_delay` で、実際のバッファの大きさが分かる。

- `disabled-by-default-webaudio.audionode`（部品ごとの記録）は付けない。記録そのものが重く、処理時間が数倍になり、ぶつぶつを悪化させる。

道具: skill `mobile-audio-render` の `scripts/trace.mjs`（記録）と `scripts/analyze.py`（集計）。`TRACE_UNTIL` に「クリアした」などの式を渡すと、そこで止める。

### 実機で切り分けるときの順番

1. 音だけのページ（skill の `scripts/audio-test.html`。開発サーバーの public に置いて開く。描画なし。正弦波 1 音 → 和音 → 和音と残響）で鳴らす。ここで鳴るなら端末やブラウザの問題。鳴らないなら、ゲーム側に原因がある。切り替えでプツッと鳴らないように、テストページでも音量は数十 ms かけて上げ下げする（いきなり止めた音はどの端末でもプツッと鳴り、判断を誤らせる）。
2. ゲームを描画なし（そういうスイッチを作る）で、自動操作で動かす。画面が黒いと人は遊べないので、自動操作と組み合わせる。減るなら描画が負荷の一部。
3. それでも残るなら、上の手順で記録を取る。端末は続けて試すと熱で遅くなり、後の結果ほど悪く出るので、比べるときは間を空ける。

## 音が小さいと、スピーカーで割れて聞こえやすい

- 音のぶつぶつとは別の症状。全体の音量（ラウドネス）が低い（例: -27 LUFS。スマホのゲームや SNS の動画は -14〜-16 くらい）。すると Android の端末では音量を大きく上げないと聞こえず、上げた状態では拍の頭の鋭い山や低い音で、小さいスピーカーがビリつく。iPhone はスピーカーの音量に余裕があるので気づきにくい。
- 対策: 出口を「低い音を削る（110Hz くらいより下。小さいスピーカーでは鳴らない）→ コンプレッサー → 持ち上げるゲイン → リミッター（`DynamicsCompressorNode` を ratio 20、attack 2ms で）」にする。録音して `ffmpeg -i rec.webm -af ebur128=peak=true -f null -` で -15 LUFS 前後、山が -1 dBFS 以下になるように合わせる。

## 処理が間に合っているのに、ぶつっ・ぷちっ・ビリッと鳴る

記録で間に合わなかった回数が 0 なのに鳴るなら、音の作り方が原因。処理が間に合わないときの音は、不規則で、重い場面ほど増える。音の作り方が原因のときは、特定の音や、拍・和音の切り替えなどの決まった瞬間に鳴り、PC で録音しても入っている。

| 鳴り方 | 原因 | 対策 |
|---|---|---|
| 音の出だし・止めで「ぷちっ」 | 音量が 0 でないところで鳴らし始めた・止めた。立ち上がりが速すぎる（4〜6ms） | 音量は 0.0001 から上げ、止めるのは十分下がってから。鋭い音でも立ち上がりは 10〜15ms にする。テストページの切り替えも同じ（いきなり止めた音はどの端末でもぷちっと鳴り、判断を誤らせる） |
| 和音や音色を切り替える瞬間に「ぶつっ」 | `cancelScheduledValues(t)` の後に `setValueAtTime(param.value, t)` で今の値から続ける書き方。`param.value` は、直前に処理した時点の値で、`t` の時点の値ではない。上げ下げの途中で止めると、値が跳ぶことがある（未検証の候補） | 使えるなら `cancelAndHoldAtTime(t)`。使えないなら、跳んでも目立たないように、切り替えを音量の小さい間にする |
| 低い音（キック・ベース）が割れたように聞こえる | コンプレッサーの立ち上がり（`attack`）が速すぎて（3ms）、低い音の 1 周期の中で波形をゆがめる | 低い音を通すコンプレッサーは `attack` を 10ms くらいにする |
| キックの後に、ざらついた低い尾が残る | ノイズから作った残響（`ConvolverNode`）にキックを送っている | 低い打楽器は残響に送らない。送るのは高めの音だけ |
| 静かな曲で、拍ごとに「チッチッ」と雑音に聞こえる | とても高いノイズ（7kHz 以上）を数 ms で立ち上げたハイハット。静かな中だと、はぜる音に聞こえる | 外すか、ずっと柔らかくする |
| 音量を上げると、拍の頭でビリつく | 全体の音量が小さいので、端末の音量を大きく上げている。小さいスピーカーが、山と低い音を鳴らしきれない | 前の節（音が小さいと…）の出口の作り方にする |
| 大きな音の瞬間だけ、少しゆがむ | 出口のリミッターの `attack` が速すぎる（2ms）（未検証の候補） | `attack` を少し遅くするか、手前で山を下げる |
| 同じ瞬間に、たくさんの音を一度に鳴らす演出（クリアの音など）で途切れる | その瞬間だけ処理が締め切りを越える。これは処理が間に合わない側の問題 | 鳴らす音を減らすか、数十 ms ずつずらす。出力バッファを大きくする |

- 調べ方: PC で録音して（遊んでいる間の出口の音を、`MediaStreamAudioDestinationNode` + `MediaRecorder` で取るなど）、波形を拡大して跳びを探す。鳴った瞬間と、そのとき鳴らした音（ログ）を突き合わせる。実機だけで鳴るときは、実機の中で同じように録って比べる。
